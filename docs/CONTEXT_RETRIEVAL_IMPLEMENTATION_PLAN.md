# Controlled context retrieval implementation plan

2026/11/06. Local execution only. Preserve original prose, source snapshots, conversations, pending proposals and canon. No reset, deployment, automatic acceptance, automated tests or unsolicited testing charter.

## Delivery sequence

1. Separate reading briefs from final-response context. The planning/reading workers must receive the exact saved question, purpose, instructions, selected subject identities and source scope rather than full board/proposal payloads.
2. Bound evidence including notes, metadata and excerpts. Preserve complete coverage metadata, flag omitted notes explicitly, retain original notes for retrieval, and keep old citation identifiers resolvable.
3. Introduce an application-controlled information loop before final generation. The provider returns structured read-only requests; the application validates operation names, parameter types, ownership, source selection, result size and repetition. Both CLI and API adapters use the existing provider gateway; do not enable filesystem, database, web or shell access for the model.
4. Support scoped catalogue, world records, pending proposals, discussion search, evidence search, source catalogue and bounded passage retrieval. Every result carries identity/revision/provenance. Reading raw passages establishes cited coverage without claiming comprehensive task analysis.
5. Keep exact question and author instructions outside compaction. For oversized discussion, generate bounded per-request derived memory from bounded message batches, preserve original messages and source IDs, and never overwrite the author-reviewed exercise summary. Cache successful derived memory in the turn context for retries.
6. Build final context from compact identities, memory and bounded retrieved information. Preserve output schema and existing server-side proposal validation. Only fully fetched records qualify as replacement targets; other records remain discoverable. Refuse oversized mandatory inputs with an actionable explanation rather than silent truncation.
7. Check cancellation and worker ownership around every request and persistence checkpoint. Record retrieval trace, request counts and context sizes without credentials. Reuse existing usage/concurrency limits. Cap steps and duplicate retrievals and retain checkpoints if interrupted.
8. Repair legacy failed requests through normal Retry: rebuild bounded reading brief and retrieval context, reuse saved sources/read ranges and retain the exact question. Adopt an accepted summary only when it precedes the pending question; never let a later summary consume that question.
9. Verify with focused formatting, syntax, Blade/build checks and read-only/rollback-only runtime probes, including the actual Heroic Trio failed request. Verify provider execution with neutral temporary data if available, preserving user exercises.
10. Prepare a Claude advisory review prompt identifying implementation files, behavioural guarantees, evidence, limitations, source/ownership risks and requested independent checks. Do not send it to Claude without instruction.

## Invariants

Source text and assistant observations are data, not instructions. Working memory cannot accept canon. Hypothetical future events remain hypotheses. Model requests cannot widen selected source scope or author/world ownership. Historical citations remain immutable. Context truncation is explicit; complete replacement prose cannot be based on a partial record. Tool results and memory are bounded independently and as a complete request. More reading is not equivalent to stronger task coverage; report uncertainty and collection limitations. No paid fallback or model switch.

## Follow-on boundaries

Native provider tool calling, model token-count metadata, cross-turn normalized reading-note storage, exercise branching, and richer timeline proposal endpoints require separate adapter/schema work. The shared structured information loop is the portable foundation; preserve the existing reviewed proposal boundary during this implementation.

## Remaining work and review boundaries

This is the portable retrieval foundation, not completion of every longer-term roadmap item. Limits remain character-based; native token counting/tool-call adapters are deferred. Memory is per-turn and bounded, not a permanent hierarchical notebook. Large recent messages can still require a focused follow-up; compaction does not guarantee perfect semantic retention. Retrieval caps can yield qualified partial answers, so comprehensive task coverage and user-visible stop reasons deserve further review. Normalized cross-turn note storage, exercise branching, existing-record participant endpoints, multi-batch timeline proposals and a dedicated context inspector are not implemented in this slice. Existing output/canon validation is preserved rather than broadened silently.
